스토어드 프로시저

저장 프로시저 · Stored Procedure · ストアドプロシージャ · SP

스토어드 프로시저는 SQL 묶음을 데이터베이스 안에 미리 저장해 두고 이름으로 부르는 것이에요. 오가는 횟수가 줄고 권한을 좁힐 수 있는 대신, 그 데이터베이스 제품에 묶여요.

1

쉽게 말하면

단골 식당에 갈 때마다 이렇게 주문한다고 해 볼게요. "면은 꼬들하게, 국물은 덜 짜게, 파는 빼고, 계란은 반숙으로, 면은 곱빼기로." 매번 다섯 마디를 해야 하고, 한 마디라도 빠뜨리면 다른 게 나와요.

그래서 사장님과 약속을 해 둬요. "그 조합을 1번 세트로 해 둡시다." 그 뒤로는 "1번이요" 한마디면 끝나요. 말이 줄고, 빠뜨릴 일도 없고, 주방도 외워 뒀으니 빨라요.

스토어드 프로시저가 이 1번 세트예요. 프로그램이 데이터베이스에 SQL을 매번 길게 보내는 대신, 자주 쓰는 묶음을 데이터베이스 안에 이름 붙여 저장해 두고 그 이름만 부르는 거예요.

무엇인가

DB 안에 저장해 둔 SQL 묶음

얻는 것

왕복 줄이기 · 권한 좁히기

치르는 값

DB 제품에 묶여요

2

그림으로 보기

같은 일을 두 방식으로 해 봐요. 오가는 횟수가 눈에 띄게 달라져요.

회원 정보를 가져오고 방문 시각을 남기는 일

-- 프로시저 없이
SELECT * FROM 회원
  WHERE 번호 = 1024;
SELECT * FROM 주문
  WHERE 회원번호 = 1024;
UPDATE 회원
  SET 마지막방문 = NOW()
  WHERE 번호 = 1024;
  -> 세 번 오가요

-- 프로시저로 묶으면
CALL 회원정보_가져오기(1024);
  -> 한 번이면 돼요

오가는 횟수 말고도 달라지는 게 여럿이에요. 아래 두 줄이 얻는 것이고, 마지막 두 줄이 치르는 값이에요.

보는 항목 매번 SQL 프로시저
오가는 횟수 보낼 때마다 한 번
보내는 것 SQL 문장 전체 이름과 값만
권한 테이블에 직접 실행만 허용
고칠 때 앱을 다시 배포해요 DB에서 바꿔요
버전 관리 코드와 함께 따로 챙겨야 해요
다른 DB로 옮길 때 비교적 쉬워요 제품에 묶여요

언제 쓸지 고르는 기준이에요. 위쪽이면 쓸 만하고, 아래쪽이면 앱에 두는 쪽이 나아요.

어느 쪽이 나은가

프로시저 수백만 건을 한꺼번에 다루는 일 · 여러 앱이 같이 지켜야 할 규칙 · 권한을 좁혀야 하는 자리
앱 쪽 자주 바뀌는 업무 규칙 · 한 앱만 쓰는 일 · 시험을 촘촘히 해야 하는 곳
가르는 질문 데이터 가까이에서 해야 빨라지는 일인가, 아니면 그냥 업무 규칙인가

1왕복이 줄어드는 게 가장 큰 효과예요. 앱과 DB가 다른 서버에 있으면 한 번 오가는 데 시간이 들어요. SQL 열 개를 따로 보내면 그 시간이 열 번 들고, 프로시저로 묶으면 한 번이에요. 건수가 많을수록 차이가 커져요.

2권한을 좁힐 수 있어요. 앱 계정에 테이블을 직접 읽고 쓸 권한을 주지 않고 "이 프로시저를 실행할 권한"만 줄 수 있어요. 그러면 앱 계정이 새어 나가도 정해진 일 말고는 못 해요.

3대신 DB 제품에 묶여요. 프로시저 문법은 제품마다 달라서 그대로 옮기지 못해요. 프로시저가 많을수록 밀결합이 깊어져서, 나중에 DB를 바꾸려 할 때 그것이 가장 큰 걸림돌이 돼요.

예시로 보기

상황 1 · SQL 주입을 막아 주나요

"프로시저를 쓰면 안전하다"는 말을 자주 듣는데 반만 맞아요.

입력을 값으로 받아 그대로 쓰면 안전해요. 사용자가 뭘 넣든 값으로만 다뤄지니 문장 구조가 안 바뀌거든요. 그런데 프로시저 안에서 글자를 이어 붙여 SQL 문장을 만들면 똑같이 뚫려요. 프로시저라는 껍데기만 썼을 뿐 안에서 하는 일은 같으니까요.

그래서 중요한 건 프로시저냐 아니냐가 아니라 값을 값으로 다루느냐예요. 앱에서 자리표시자를 쓰는 방식도 같은 보호를 해 줘요. WAF는 그 위에 덧대는 그물이지 이 문제의 답은 아니에요.

상황 2 · 왜 요즘은 덜 쓸까요

예전에는 업무 규칙을 통째로 프로시저에 넣는 곳이 많았어요. 지금은 앱 쪽에 두는 경우가 늘었는데, 이유가 몇 가지 있어요.

코드가 DB 안에 있어서 잘 안 보여요. 저장소를 뒤져도 안 나오니 누가 언제 왜 바꿨는지 따라가기 어렵고, 배포 절차도 따로 챙겨야 해요. 시험하기도 번거로워요. 앱 코드는 가볍게 돌려 볼 수 있지만 프로시저는 DB를 띄워야 하죠.

무게 문제도 커요. 앱 서버는 늘리기 쉬운데 DB 서버는 늘리기 어려워요. 계산을 프로시저로 몰면 가장 늘리기 힘든 자리에 일을 쌓는 셈이에요. 그리고 로직이 앱과 DB 두 군데로 갈려서 어디를 고쳐야 하는지 찾는 데 시간이 들어요.

상황 3 · 그래도 프로시저가 이기는 자리

덜 쓴다고 쓸모없어진 건 아니에요. 데이터가 아주 많을 때는 여전히 프로시저 쪽이 분명히 빨라요.

수백만 건을 집계한다고 해 볼게요. 앱에서 하려면 그 데이터를 전부 앱으로 끌어와야 해요. 그 자체로 엄청난 시간과 회선이 들죠. 프로시저는 데이터가 있는 자리에서 계산하고 결과만 돌려줘요. 밤에 도는 정산·집계 같은 일이 대표적이에요.

여러 앱이 같은 DB를 쓸 때도 그래요. 같은 규칙을 앱마다 따로 구현하면 언젠가 서로 달라져요. 한 곳에 두면 그럴 일이 없고요. ORM이 SQL을 앱 쪽으로 끌어오는 방향이라면, 프로시저는 반대 방향이에요. 어느 쪽이 맞는지는 다루는 양과 쓰는 앱 수로 갈려요.

프로시저를 쓸지 말지보다 중요한 게 하나 있어요. 쓰기로 했으면 코드처럼 다루는 것이에요. 저장소에 파일로 두고, 바뀐 내역을 남기고, 배포 절차에 넣는 거예요. DB 관리 화면에서 바로 고치고 끝내는 순간, 아무도 지금 뭐가 돌고 있는지 모르는 상태가 돼요.

한 줄 정리

단골집 1번 세트예요. 말이 줄고 빨라지는 대신, 그 집에 묶여요.
