Django ORM

장고 ORM · 객체 관계 매핑 · Object-Relational Mapping · QuerySet · 마이그레이션

Django ORM은 파이썬 코드를 SQL로 바꿔 데이터베이스와 대화해 주는 번역기예요. 표는 클래스로, 줄 하나는 객체로 다뤄요.

카페 사장님이 창고 담당자에게 "5천 원 넘는 메뉴 재고 좀 알려 줘요"라고 말로 부탁해요. 담당자는 그 말을 창고 장부의 형식으로 바꿔 찾아본 뒤, 결과를 정리해 돌려줘요. 사장님은 장부 쓰는 법을 몰라도 돼요.

Django ORM이 그 담당자예요. 우리는 Menu.objects.filter(price__gt=5000)처럼 파이썬으로 말하고, ORM이 이걸 데이터베이스의 말인 SQL로 바꿔 물어본 뒤, 결과를 파이썬 객체로 담아 줘요. ORM은 Object-Relational Mapping, 곧 객체와 표를 짝지어 준다는 뜻이에요.

01모델 = 테이블

클래스 하나가 표 하나, 필드 하나가 열 하나예요. 줄마다 붙는 번호 id는 Django가 알아서 만들어 줘요.

cafe/models.py

from django.db import models

class Category(models.Model):
    name = models.CharField(max_length=50)

class Menu(models.Model):
    name = models.CharField(max_length=50)    # 글자 칸
    price = models.IntegerField()             # 숫자 칸
    stock = models.IntegerField(default=0)    # 비워 두면 0
    category = models.ForeignKey(Category, on_delete=models.CASCADE, related_name="menus")
모델 클래스 Menu=표 cafe_menu 필드 price=열 price 객체 하나 latte=줄(행) 하나 QuerySet=SELECT … 문

표 이름은 앱 이름_모델 이름으로 정해져요. 위 코드라면 cafe_menu예요.

02마이그레이션 — 모델 변경을 DB에 옮기기

모델을 고쳐도 데이터베이스는 저절로 바뀌지 않아요. 먼저 바뀐 점을 변경 설계도 파일로 적고(makemigrations), 그 설계도대로 표를 고쳐요(migrate). 설계도 파일은 git에 함께 올려서 팀원 DB도 같은 모양으로 맞춰요.

터미널

$ python manage.py makemigrations  # 모델 변화 → 설계도 파일
Migrations for 'cafe':
  cafe/migrations/0001_initial.py
    + Create model Category
    + Create model Menu
$ python manage.py sqlmigrate cafe 0001  # 실제로 돌 SQL 미리 보기
$ python manage.py migrate  # 설계도대로 표를 만들거나 고쳐요
$ python manage.py showmigrations  # 어디까지 적용됐나

이미 다른 사람과 나눠 쓴 마이그레이션 파일은 고치지 말고, 새 파일을 하나 더 만들어 바꾸는 게 안전해요.

03Manager와 QuerySet — 게으른 주문서

Menu.objects가 Manager예요. 표로 들어가는 창구죠. 여기서 all(), filter()를 부르면 QuerySet이 나와요. QuerySet은 조건을 이어 붙일 수 있고, 정말 필요할 때까지 DB에 가지 않아요.

python manage.py shell

qs = Menu.objects.filter(price__gte=4500)   # 아직 DB에 안 가요
qs = qs.order_by("-price")                  # 조건을 더 쌓을 뿐
print(qs.query)                             # 만들어질 SQL 보기
for menu in qs:                             # 여기서 처음 DB에 가요
    print(menu.name, menu.price)

for로 돌거나 list(), len()을 부를 때 비로소 SQL이 날아가요. 한 번 꺼낸 QuerySet은 결과를 기억해 두지만, filter()를 새로 붙이면 새 QuerySet이라 다시 DB에 가요.

04기본 CRUD — 만들고, 읽고, 고치고, 지우기

python manage.py shell

coffee = Category.objects.create(name="커피")                       # C 만들기
latte = Menu.objects.create(name="라떼", price=5000, category=coffee)
latte = Menu.objects.get(name="라떼")          # R 딱 한 줄
cheap = Menu.objects.filter(price__lt=5000)   # R 여러 줄 (없으면 빈 묶음)
latte.price = 5500
latte.save()                                  # U 한 줄 고치기
Menu.objects.filter(stock=0).update(stock=10) # U 여러 줄을 한 번에
latte.delete()                                # D 지우기

get()은 맞는 줄이 없으면 DoesNotExist, 둘 이상이면 MultipleObjectsReturned 오류를 내요. 없을 수도 있으면 filter()를 쓰세요. QuerySet의 update()는 SQL 한 번으로 끝내는 대신 각 객체의 save()를 부르지 않아요.

05조건 쓰기 — 룩업, Q, F

룩업은 필드__조건처럼 밑줄 두 개로 조건을 붙이는 문법이에요(gte 이상, lt 미만, contains 포함, in 목록 중 하나 등). filter()에 여러 개를 쉼표로 쓰면 "그리고"예요. "또는"과 "아니다"는 Q로, 다른 칸 값을 쓰거나 DB 안에서 계산할 땐 F로 써요.

python manage.py shell

from django.db.models import Q, F

Menu.objects.filter(price__gte=5000, stock__gt=0)       # 그리고
Menu.objects.filter(name__contains="케이크")              # 글자 포함
Menu.objects.filter(category__name="커피")               # 관계를 건너 조건
Menu.objects.filter(Q(price__lt=4500) | Q(stock=0))      # 또는
Menu.objects.filter(~Q(category__name="커피"))           # 아니다
Menu.objects.update(price=F("price") + 500)             # DB 안에서 계산

F가 중요한 이유: menu.stock -= 1 후 save()는 값을 파이썬으로 가져와 빼고 다시 써요. 두 사람이 동시에 하면 한 번만 빠질 수 있어요. F("stock") - 1은 DB가 직접 빼므로 이 틈이 없어요.

06관계 — ForeignKey, ManyToMany, 거꾸로 건너기

ForeignKey는 "여러 메뉴가 한 분류에 속한다"(다대일)예요. on_delete는 꼭 정해야 하고, CASCADE면 분류를 지울 때 그 메뉴들도 함께 지워져요. ManyToManyField는 "메뉴 하나에 태그 여럿, 태그 하나에 메뉴 여럿"(다대다)이에요. 둘을 잇는 중간 표는 Django가 만들어 줘요.

cafe/models.py (추가)

class Tag(models.Model):
    name = models.CharField(max_length=30)

class Menu(models.Model):
    # ...앞의 칸들은 그대로
    tags = models.ManyToManyField(Tag, blank=True)    # 중간 표 cafe_menu_tags

관계는 양쪽에서 건널 수 있어요. 메뉴에서 분류로 가는 게 정방향, 분류에서 메뉴들로 가는 게 역방향이에요. 역방향 이름은 related_name으로 정하고, 안 정하면 모델 이름_set이 돼요.

python manage.py shell

latte.category.name              # 정방향: 메뉴 → 분류
coffee.menus.all()               # 역방향: 분류 → 메뉴들 (related_name="menus")
hot = Tag.objects.create(name="따뜻한")
latte.tags.add(hot)              # 다대다 잇기 (remove, set, clear도 있어요)
hot.menu_set.all()               # related_name이 없으면 menu_set
Category.objects.filter(menus__price__gte=6000).distinct()  # 역방향으로 건너 조건

역방향으로 건너 조건을 걸면 JOIN 때문에 같은 분류가 여러 번 나올 수 있어요. 한 번씩만 보려면 distinct()를 붙여요.

07성능 — N+1 문제

메뉴 목록을 꺼내 1번, 그다음 메뉴마다 분류를 물으러 1번씩 더 가요. 메뉴가 N개면 1 + N번이에요. 코드는 멀쩡해 보여서 더 무서워요. 미리 같이 꺼내 오라고 알려 주면 해결돼요.

python manage.py shell

for menu in Menu.objects.all():                        # 1번
    print(menu.name, menu.category.name)               # 메뉴마다 1번씩 더 → N+1

for menu in Menu.objects.select_related("category"):   # JOIN으로 한 번에
    print(menu.name, menu.category.name)

for menu in Menu.objects.prefetch_related("tags"):     # 메뉴 1번 + 태그 1번
    print(menu.name, [t.name for t in menu.tags.all()])

메뉴 3개로 세어 보니 쿼리가 4번 → 1번 → 2번이었어요. select_related는 정방향 ForeignKey·OneToOne을 JOIN으로, prefetch_related는 다대다·역방향을 따로 한 번 더 물어 파이썬에서 짝지어 가져와요.

08트랜잭션 — 다 되거나, 다 안 되거나

"재고 빼기"와 "결제"는 함께 성공하거나 함께 취소돼야 해요. 재고만 빠지고 결제가 실패하면 안 되죠. transaction.atomic() 블록 안에서 오류가 나면 그 안의 변경이 모두 되돌려져요(롤백).

python manage.py shell

from django.db import transaction
from django.db.models import F

with transaction.atomic():                                         # 여기부터 한 묶음
    Menu.objects.filter(pk=latte.pk).update(stock=F("stock") - 1)
    pay(order)                                                     # 결제 함수(예시)에서 오류가 나면…
# …재고 빼기도 함께 취소돼요

같은 줄을 여러 사람이 동시에 고칠 수 있다면 atomic() 안에서 select_for_update()로 그 줄을 잠가요. 데이터베이스 설정에서 ATOMIC_REQUESTS를 켜면 요청 하나를 통째로 한 묶음으로 처리해요.

09집계 — 전체를 하나로, 줄마다 하나씩

aggregate()는 표 전체를 숫자 하나로 줄여 딕셔너리로 돌려줘요. annotate()는 줄마다 계산한 값을 붙여 줘요. SQL의 GROUP BY에 해당해요.

python manage.py shell

from django.db.models import Avg, Count, Sum

Menu.objects.aggregate(Avg("price"), total=Sum("stock"))
# 결과는 딕셔너리: {'price__avg': ..., 'total': ...}

for c in Category.objects.annotate(n=Count("menus")):
    print(c.name, c.n)            # 분류마다 메뉴가 몇 개인지

이름을 안 주면 필드__함수(예: price__avg)가 키가 돼요. 개수만 필요할 때 len(qs) 대신 qs.count()를 쓰면 줄을 다 꺼내 오지 않아요.

10디버깅 습관

ORM 덕분에 SQL을 몰라도 되지만, 실제로 날아가는 SQL은 보면서 쓰는 게 좋아요.

python manage.py shell

print(qs.query)                  # 만들어질 SQL
print(qs.explain())              # DB가 어떻게 찾는지 (인덱스를 쓰나)

from django.db import connection
print(len(connection.queries))   # 지금까지 날린 쿼리 수 (DEBUG=True일 때만)
  • 화면이 느리면 코드보다 먼저 쿼리 수를 세요. django-debug-toolbar를 쓰면 페이지마다 보여 줘요.
  • 반복문 안에서 점(.)으로 관계를 건너고 있다면 N+1을 의심해요.
  • 있는지만 볼 땐 exists(), 개수만 볼 땐 count(). 단, 어차피 데이터를 쓸 거라면 한 번 꺼내 쓰는 게 더 빨라요.
  • 테스트에 assertNumQueries로 쿼리 수를 박아 두면, N+1이 다시 생겼을 때 바로 알아요.
  • 새 조건은 python manage.py shell에서 먼저 쳐 보고 qs.query를 확인한 뒤 코드에 옮겨요.

한 줄 정리

표는 클래스로, 질문은 QuerySet으로. 날아가는 SQL은 꼭 확인해요.
